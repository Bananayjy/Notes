# 响应式编程

## 一、前置知识点

### 1、Servlet

Servlet 是 Java Web 的基石规范，是运行在服务器端、用来处理 HTTP 请求的 Java 组件，是一个**规范（接口）**，它规定了“怎么处理请求”，但本身不提供运行环境。你可以把它理解成：一个能接收 HTTP 请求、并返回 HTTP 响应的 Java 类。它的核心接口是 `jakarta.servlet.Servlet`（旧版是 `javax.servlet.Servlet`），最核心的方法是：

```java
void service(ServletRequest req, ServletResponse res)
```

### 2、Tomcat

1、概述

Tomcat 是 Servlet 规范的实现，也就是 Servlet 容器。

```
Servlet 规范（接口/标准）  ←→  Tomcat（Servlet 容器/实现）
```

Servlet 规范定义的接口（`jakarta.servlet.*`）→ Tomcat 里的实现类（`org.apache.catalina.*`）：

| 规范接口              | Tomcat 实现类                       | 作用                  |
| :-------------------- | :---------------------------------- | :-------------------- |
| `ServletContext`      | `ApplicationContext`                | 整个 Web 应用的上下文 |
| `HttpServletRequest`  | `RequestFacade`（包装 `Request`）   | 封装一次请求          |
| `HttpServletResponse` | `ResponseFacade`（包装 `Response`） | 封装一次响应          |
| `ServletConfig`       | `StandardWrapperFacade`             | Servlet 配置信息      |
| `FilterChain`         | `ApplicationFilterChain`            | 过滤器链              |
| `HttpSession`         | `StandardSessionFacade`             | 会话                  |
| `RequestDispatcher`   | `ApplicationDispatcher`             | 请求转发/包含         |



2、职责/功能

（1）监听端口、解析 HTTP 报文

规范里根本没规定 HTTP 怎么解析（那是 HTTP 协议的事），Tomcat 要自己实现：

```
// Tomcat 源码（简化）：CoyoteAdapter / Http11Processor
// 它把一行行字节流解析成：
//   method="GET"
//   uri="/hello"
//   queryString="name=Tom"
//   headers={Host:..., User-Agent:...}
//   body=...
```

这部分完全是 Tomcat 自己写的，规范不涉及。

（2）创建 Request / Response 对象

这一步是规范要求的（规范说：容器必须给 Servlet 传 Request/Response），Tomcat 完成创建

Tomcat 在 `CoyoteAdapter.service()` 里：

```
// 简化版 Tomcat 源码逻辑
public void service(org.apache.coyote.Request req, org.apache.coyote.Response res) {
    // ① 创建实现了 HttpServletRequest 的对象
    Request request = (Request) req.getNote(ADAPTER_NOTES);
    if (request == null) {
        request = connector.createRequest();   // ← new Request()
    }
    
    // ② 创建实现了 HttpServletResponse 的对象
    Response response = connector.createResponse();  // ← new Response()

    // ③ 绑定
    request.setResponse(response);
    response.setRequest(request);

    // ④ 交给容器继续处理
    postParseRequest(req, request, res, response);
    ...
}
```

（3）管理 Servlet 生命周期

规范规定了生命周期：`init → service → destroy`，但**谁调用、何时调用**是容器的事。

Tomcat 里的核心类：`StandardWrapper`（每个 Servlet 对应一个 Wrapper）。

```
// Tomcat 源码简化：StandardWrapper.allocate()
public Servlet allocate() throws ServletException {
    if (instance == null) {
        // ① 反射创建 Servlet 实例（调用你的无参构造）
        instance = loadServlet();  
        // loadServlet 内部：
        //   Class<?> clazz = Class.forName(servletClass);
        //   Servlet servlet = (Servlet) clazz.getDeclaredConstructor().newInstance();
        
        // ② 调用 init()，传入 ServletConfig
        instance.init(new StandardWrapperFacade(this));
    }
    return instance;
}

// Tomcat 源码简化：StandardWrapperValve.invoke()
public void invoke(Request request, Response response) {
    // ① 分配（创建或复用）Servlet 实例
    servlet = wrapper.allocate();
    
    // ② 构造 FilterChain
    ApplicationFilterChain chain = ...;
    
    // ③ 调用 Servlet 的 service()  ← 这是关键！
    chain.doFilter(request.getRequest(), response.getResponse());
    
    // 最终会走到：
    // servlet.service(request, response);
}
```

（4）把请求"分发"到对应的 Servlet

规范没规定 URL 怎么匹配（除了定义匹配规则的语义）。Tomcat 里的 `Mapper` 负责：

```
// Tomcat 源码简化：Mapper.map()
// 输入：/hello
// 输出：对应的 StandardWrapper（也就是你的 HelloServlet）
```

Tomcat 支持这些匹配规则（**Tomcat 的具体实现**）：

- 精确匹配：`/hello`
- 前缀匹配：`/user/*`
- 扩展名匹配：`*.do`
- 默认匹配：`/`

然后在 `StandardContext` 里维护 `MappedWrapper[]` 数组做查找。

（5）把 Response 数据写回成 HTTP 报文

规范只定义了 `getWriter()` 这个方法名，具体怎么变成字节流、怎么加响应头，是 Tomcat 实现。

```
// 你写的代码：
resp.getWriter().println("<h1>Hello, Tom!</h1>");

// Tomcat 背后做的事（Http11OutputBuffer）：
// 组装成：
// HTTP/1.1 200 OK\r\n
// Content-Type: text/html;charset=UTF-8\r\n
// Content-Length: 25\r\n
// \r\n
// <h1>Hello, Tom!</h1>
// 然后通过 Socket 发出去
```

（6）管理 Session

规范定义了 `HttpSession` 接口，Tomcat 实现了它（`StandardSession`）并负责创建/销毁/序列化。

```
// 你写的代码：
HttpSession session = req.getSession();

// Tomcat 背后：
// ① 从 Cookie 里读 JSESSIONID
// ② 找不到 → 创建 StandardSession 对象，生成新的 JSESSIONID
// ③ 放入 Manager（会话管理器），比如 StandardManager
// ④ 响应时 Set-Cookie: JSESSIONID=xxx
```



3、Tomcat和Servlet的关系

类比一下，`Servlet` 规范 ≈ JDBC 接口（`Connection`、`Statement`），`Tomcat` ≈ MySQL 驱动（JDBC 的具体实现，你写的 Servlet ≈ 用 JDBC 接口写业务代码的人。Servlet 规范定义"怎么和容器交互"，Tomcat 负责"解析 HTTP + 调用你的 Servlet + 生成响应"，你只需要专注于 `doGet/doPost` 里的业务逻辑。

- **Servlet 规范**：由 Java 官方（原 Sun，现 Oracle/Eclipse）制定的一套**接口和标准**，定义在 `jakarta.servlet`（旧版 `javax.servlet`）包中。

  - `Servlet` 接口

  - `HttpServlet` 抽象类

  - `ServletRequest` / `ServletResponse`

  - `HttpServletRequest` / `HttpServletResponse`

  - `ServletContext`、`Filter`、`Listener` 等

- **Tomcat**：是一个 **Servlet 容器（Web 容器）**，它**实现了 Servlet 规范**。

  - 负责解析 HTTP 请求 → 封装成 `HttpServletRequest`

  - 调用你写的 Servlet 的 `service()` / `doGet()` / `doPost()`

  - 把你写的响应 → 转成 HTTP 响应报文发回浏览器

  - 管理 Servlet 的**生命周期**（加载、实例化、init、service、destroy）

**其他 Servlet 容器**：Jetty、Undertow、WebLogic、WebSphere 等，都实现了同一套规范。



4、http请求/响应示例

假设浏览器访问：`http://localhost:8080/hello?name=Tom`

HTTP 请求报文（浏览器 → 服务器）：

```
GET /hello?name=Tom HTTP/1.1
Host: localhost:8080
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Accept: text/html,application/xhtml+xml
Accept-Language: zh-CN,zh;q=0.9
Connection: keep-alive
```

对应的Servlet代码（应用侧的Servlet接口实现）：

```java
@WebServlet("/hello")
public class HelloServlet extends HttpServlet {

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {

        // 1. 读取请求参数（Tomcat 已帮我们解析好 URL 和 Header）
        String name = req.getParameter("name");   // "Tom"
        String ua = req.getHeader("User-Agent");  // 浏览器信息

        // 2. 设置响应状态和头
        resp.setStatus(200);
        resp.setContentType("text/html;charset=UTF-8");

        // 3. 写出响应体
        PrintWriter out = resp.getWriter();
        out.println("<h1>Hello, " + name + "!</h1>");
        out.println("<p>你的浏览器是: " + ua + "</p>");
    }
}
```

HTTP 响应报文（服务器 → 浏览器）：

```
HTTP/1.1 200 OK
Content-Type: text/html;charset=UTF-8
Content-Length: 62
Date: Tue, 01 Oct 2026 10:00:00 GMT
Server: Apache-Coyote/1.1

<h1>Hello, Tom!</h1>
<p>你的浏览器是: Mozilla/5.0 (Windows NT 10.0; Win64; x64)</p>
```

调用流程：

```
浏览器
  │  ① 发送 HTTP 请求报文
  ▼
Tomcat（Servlet 容器）
  │  ② 解析报文，封装成 HttpServletRequest
  │  ③ 找到 @WebServlet("/hello") 对应的 Servlet
  │  ④ 调用 doGet(req, resp)
  ▼
你的 HelloServlet
  │  ⑤ 通过 req 读参数、通过 resp 写内容
  ▼
Tomcat
  │  ⑥ 把 resp 的内容组装成 HTTP 响应报文
  ▼
浏览器
```



5、线程池和NIO模型

（1）线程池

| 阶段                     | 谁在跑      | 线程池            |
| :----------------------- | :---------- | :---------------- |
| 接收请求、调用 service() | Tomcat 线程 | Tomcat 请求处理池 |
| 业务处理（慢操作）       | 你的线程    | 你自建的线程池    |
| 写响应、发回客户端       | Tomcat 线程 | Tomcat 请求处理池 |

- 线程池 1：Tomcat 的请求处理线程池

这是 Tomcat 内置的，叫 **`Executor`**（在 `server.xml` 里配置），底层就是 `ThreadPoolExecutor`。

- **职责**：接收 socket、解析 HTTP、调用 `DispatcherServlet.service()`
- **线程名**：`http-nio-8080-exec-1`、`-2`……
- **关键**：`service()` 一返回，这个线程立刻被归还给池子，可以去处理新请求

它**不负责**你的业务逻辑，只负责“把请求接进来、把响应发出去”。

- 线程池 2：你自己的业务线程池

`request.startAsync()` 之后，`service()` 就返回了，Tomcat 线程走了。那谁来执行“慢慢处理”的业务？没有人替你管。必须你自己提供一个线程池。



（2）线程池使用完整流程：

```
① 浏览器发请求
        │
        ▼
② Tomcat 线程池（http-nio-8080-exec-N）
   调用 DispatcherServlet.service()
        │
        ▼
③ service() 里调用 request.startAsync()
   拿到 AsyncContext
        │
        ▼
④ service() 返回 ──────────────► Tomcat 线程归还池子 ✅
        │
        │ （业务逻辑交给业务线程池）
        ▼
⑤ 业务线程池（你自己建的）
   执行慢操作
        │
        ▼
⑥ 处理完，通过 AsyncContext 写响应
   asyncContext.getResponse()...write(...)
   asyncContext.complete()
        │
        ▼
⑦ Tomcat 负责把响应发回客户端
   （这一步可能由 Tomcat 线程池里的某个线程完成）
```



为什么这么设计？

如果是传统同步 Servlet：

```
请求进来 → Tomcat 线程 → 执行业务（阻塞等 DB/下游）→ 返回 → 线程归还
```

慢操作期间，Tomcat 线程被**死死占住**。假设 Tomcat 最大 200 线程，200 个慢请求就能把整个服务打满，第 201 个请求直接被拒绝。

异步之后：

```
请求进来 → Tomcat 线程只负责接 → 立刻归还 → 业务在另一个池子慢慢跑
```

Tomcat 线程不再被慢操作阻塞，它能接更多请求。并发能力从“受 Tomcat 线程数限制”变成“受你自己的业务线程池限制”——而后者你可以按需调整。



（3）NIO模型

Tomcat NIO 模型主要依赖三大线程角色：

1. **Acceptor 线程**
   - **职责**：专门负责**接收 TCP 连接**。
   - **工作**：服务器启动后，Acceptor 在 `ServerSocketChannel` 上阻塞等待。一旦有客户端连接进来，它就接收该连接，并将其注册到 **Poller** 的 `Selector` 上。
   - **数量**：通常只有 **1 个**。
2. **Poller 线程**
   - **职责**：负责**监听 I/O 事件**（如数据可读，I/O 多路复用）。
   - **工作**：每个 Poller 拥有一个 `Selector`，循环调用 `select()` 监听注册在其上的所有连接。当某个连接有数据可读时，Poller 将任务封装成 `SocketProcessor`，扔给 **Executor 线程池**。
   - **数量**：默认为 **1 个**（在较新版本中，如果 CPU 核数较多，可能会启动多个 Poller 来分担压力）。
3. **Executor 线程池**
   - **职责**：负责**处理具体的 HTTP 请求**。
   - **工作**：线程池中的工作线程从队列中取出 `SocketProcessor`，解析 HTTP 报文，调用对应的 **Servlet** 的 `service()` 方法，执行业务逻辑，并写回响应。
   - **数量**：可配置，默认 `maxThreads` 为 **200**。



一个请求的完整处理流程如下：

```
浏览器                Tomcat                                    Spring MVC
  │                     │                                          │
  │──TCP 三次握手──────→│ Acceptor 接收连接                        │
  │                     │   └→ 注册到 Poller 的 Selector           │
  │──HTTP 请求报文─────→│ Poller select() 检测到读就绪              │
  │                     │   └→ 封装 SocketProcessor → Executor 线程池
  │                     │ Executor 线程：解析 HTTP                   │
  │                     │   └→ Mapper 路由到 DispatcherServlet      │
  │                     │   └→ 适配 Request → Valve 管道            │
  │                     │   └→ 调用 DispatcherServlet.service() ──→│
  │                     │                                          │ HandlerMapping 查找
  │                     │                                          │ HandlerAdapter 调用
  │                     │                                          │ UserController.getUser(1)
  │                     │                                          │ 业务处理 50ms
  │                     │                                          │ 返回 User 对象
  │                     │                                          │ 序列化为 JSON
  │                     │←── 写入 HttpServletResponse ─────────────│
  │                     │ Executor 线程写回 SocketChannel           │
  │←──HTTP 响应报文─────│                                          │
  │                     │ 连接保持（keep-alive）                    │
```

| 阶段      | 负责组件                       | 核心动作                         |
| :-------- | :----------------------------- | :------------------------------- |
| 连接建立  | Acceptor                       | 接收 TCP，注册到 Poller          |
| I/O 监听  | Poller                         | select() 发现读就绪，派发任务    |
| HTTP 解析 | Executor                       | 读字节，解析 HTTP，封装 Request  |
| 容器路由  | Mapper + Valve                 | 找到 DispatcherServlet，走管道   |
| 业务处理  | DispatcherServlet + Controller | 查找 Handler，反射调用，执行业务 |
| 响应写回  | Executor + Poller              | 序列化，写 SocketChannel         |

**一句话总结**：Acceptor 管"接客"，Poller 管"看谁有话要说"，Executor 管"听内容、干活、回话"，DispatcherServlet 管"把活派给具体的 Controller"。整个过程中，Executor 线程从解析 HTTP 到业务处理再到写回响应，全程阻塞，这就是同步 HTTP 请求的本质。



场景设定：

- Tomcat 端口：8080
- Spring MVC 应用，有一个 Controller：

```
@RestController
public class UserController {
    @GetMapping("/user/{id}")
    public User getUser(@PathVariable Long id) {
        return userService.findById(id); // 模拟业务处理耗时 50ms
    }
}
```



第一阶段：TCP 连接建立（Acceptor）

**1. 浏览器发起 TCP 连接**

浏览器向 `localhost:8080` 发起三次握手。Tomcat 启动时，**Acceptor 线程**已经在 `ServerSocketChannel` 上阻塞等待。

**2. Acceptor 接收连接**

三次握手完成后，Acceptor 从 `accept()` 返回，拿到一个 `SocketChannel`。它把这个连接**注册到某个 Poller 的 Selector 上**，监听 `OP_READ` 事件。

```
Acceptor 线程：收到新连接 → 注册到 Poller 的 Selector → 继续 accept 下一个
```

注意：此时 HTTP 请求数据可能还没到达，Acceptor 只负责"接收连接"，不负责"读数据"。



第二阶段：数据到达与 I/O 监听（Poller）

**3. 浏览器发送 HTTP 请求报文**

浏览器通过已建立的 TCP 连接，发送：

```
GET /user/1 HTTP/1.1
Host: localhost:8080
Accept: application/json
```

这些数据经过 TCP 层，到达 Tomcat 所在机器的网卡，最终进入内核缓冲区。

**4. Poller 检测到"读就绪"**

Poller 线程循环调用 `selector.select()`。当内核通知"某个连接的读缓冲区有数据了"，`select()` 返回。

Poller 找到对应的 `SocketChannel`，将其封装成一个 **`SocketProcessor`** 任务，**提交给 Executor 线程池**。

```
Poller 线程：select() 返回 → 找到就绪的 Channel → 封装 SocketProcessor → 扔进线程池队列
```

Poller 不读数据、不解析 HTTP，只负责"发现哪个连接有数据"，然后转交。



第三阶段：HTTP 解析（Executor 线程）

**5. Executor 工作线程处理 SocketProcessor**

线程池中某个空闲线程（假设是 `http-nio-8080-exec-5`）取出 `SocketProcessor`，开始真正的工作：

- **读取数据**：从 `SocketChannel` 读取字节流
- **解析 HTTP**：按 HTTP 协议解析请求行、请求头、请求体
- **封装对象**：生成 Tomcat 内部的 `Request` 和 `Response` 对象

此时，Tomcat 知道了：

- 请求方法：`GET`
- 请求路径：`/user/1`
- 协议版本：`HTTP/1.1`
- 请求头：`Host: localhost:8080` 等

```
Executor 线程：读字节 → 解析 HTTP → 得到 method=GET, uri=/user/1 → 准备路由
```



第四阶段：Tomcat 容器路由（Mapper + Valve 管道）

**6. Mapper 路由**

```
Engine (Catalina)
  └── Host (localhost)
        └── Context (/ 或 /myapp)   ← 根据 contextPath 匹配
              └── Wrapper (dispatcherServlet)  ← 根据 url-pattern 匹配
```

对于 Spring MVC 应用，`web.xml` 或 `WebApplicationInitializer` 中通常配置

```
<servlet-mapping>
    <servlet-name>dispatcher</servlet-name>
    <url-pattern>/</url-pattern>
</servlet-mapping>
```

所以 `/user/1` 会匹配到 **DispatcherServlet** 这个 Wrapper。

**7. 构建 Servlet 规范的 Request/Response**

`CoyoteAdapter` 将 Tomcat 内部的 `Request`/`Response` 适配为符合 Servlet 规范的：

- `HttpServletRequest`
- `HttpServletResponse`

**8. 流经 Valve 管道**

请求依次经过 Engine、Host、Context、Wrapper 的 Valve（阀门），执行访问日志、IP 过滤等逻辑。

**9. 调用 DispatcherServlet.service()**

最终 `WrapperValve` 调用 `DispatcherServlet` 的 `service()` 方法。

```
Executor 线程：Mapper 找到 DispatcherServlet → 适配 Request → 走 Valve 管道 → 调用 service()
```

> 到这里，Tomcat 的职责基本结束，控制权交给 Spring MVC。



第五阶段：Spring MVC 处理（DispatcherServlet）

**10. DispatcherServlet 查找 Handler**

`DispatcherServlet` 调用 `HandlerMapping`（`RequestMappingHandlerMapping`），根据 `/user/1` 和 `GET` 方法查找映射。

启动时 Spring 已经扫描了 `@GetMapping("/user/{id}")`，注册了映射关系。此时匹配到：

text

```
HandlerMethod: UserController.getUser(Long id)
拦截器链: []（假设没有自定义拦截器）
```

**11. HandlerAdapter 执行 Handler**

`DispatcherServlet` 找到 `RequestMappingHandlerAdapter`，由它负责：

- **参数解析**：`@PathVariable Long id` → 从 URL 中提取 `1`，转为 `Long`
- **反射调用**：执行 `userController.getUser(1L)`

**12. 执行业务逻辑**

```
userService.findById(1L); // 模拟耗时 50ms，可能查数据库
```

这 50ms 内，**Executor 线程一直阻塞等待**，直到业务返回。

**13. 处理返回值**

`@RestController` = `@Controller` + `@ResponseBody`，所以返回值不走 ViewResolver，而是由 `HttpMessageConverter`（如 `MappingJackson2HttpMessageConverter`）将 `User` 对象序列化为 JSON：

```
{"id": 1, "name": "张三", "age": 25}
```

```
DispatcherServlet：找到 HandlerMethod → 参数绑定 → 反射调用 → 得到 User 对象 → 序列化为 JSON
```

> 补充：关键配置参数
>
> 在 `server.xml` 的 `<Connector>` 标签中，可以调整 NIO 模型的行为：
>
> - `protocol`：设置为 `org.apache.coyote.http11.Http11NioProtocol` 即启用 NIO 模型（Tomcat 8 以后默认就是 NIO）。
> - `acceptorThreadCount`：Acceptor 线程数，默认 1。
> - `pollerThreadCount`：Poller 线程数，默认 1（或根据 CPU 核数调整）。
> - `maxThreads`：Executor 线程池最大线程数，默认 200。
> - `acceptCount`：当所有 Executor 线程都在忙时，新连接进入的等待队列长度。



第六阶段：响应写回（Executor 线程 → Poller → 客户端）

**14. 写入 Response**

`DispatcherServlet` 将 JSON 写入 `HttpServletResponse` 的输出流。Tomcat 将其封装为 HTTP 响应报文：

```
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 32

{"id": 1, "name": "张三", "age": 25}
```

**15. Executor 线程写回数据**

Executor 线程将响应字节写入 `SocketChannel`。如果一次写不完（比如响应很大、TCP 缓冲区满），会注册 `OP_WRITE` 事件，由 **Poller** 后续继续监听可写事件，再触发写操作。

**16. 连接管理**

- HTTP/1.1 默认 `keep-alive`，TCP 连接**不关闭**，Executor 线程归还线程池，等待下一个请求复用该连接。
- 如果是 HTTP/1.0 或 `Connection: close`，则关闭 TCP 连接。

```
Executor 线程：写响应 → 若写完 → 归还线程池 → 连接保持或关闭
```

**17. 浏览器渲染**

浏览器收到 JSON 响应，前端 JavaScript 解析并渲染页面。



### 3、Servlet 容器的异步支持（AsyncContext）

传统 Servlet 是**阻塞模型**：

```
请求进来 → Tomcat 分配一个线程 → 调 service() → 
service() 里可能等数据库、等下游接口（阻塞）→ 
处理完返回 → 线程归还
```

这个线程从请求进来到响应返回，全程被占用。如果业务里有慢操作（等 I/O），线程就干等着。并发一高，Tomcat 的线程池很快耗尽。



Servlet 3.0 引入了异步支持。核心思路是：把“接收请求”和“处理请求”分开，让容器线程尽早归还：

```
请求进来 → Tomcat 线程调用 service() → 
service() 里启动异步：request.startAsync() 拿到 AsyncContext → 
service() 立刻返回，Tomcat 线程被释放（可以去处理别的请求）→ 
业务在另一个线程里慢慢处理 → 
处理完调用 asyncContext.complete() 或 getResponse().getWriter().write(...) → 
响应发回客户端
```

关键对象就是 **`AsyncContext`**：它代表了“这个请求还没结束，但容器线程可以先走了，我稍后自己完成它”。



### 4、Spring MVC 和 DispatcherServlet

1、概述

Spring MVC 是构建在 Servlet 之上的一个 Web 框架。

Servlet 只提供最底层的“接收请求、返回响应”，但真实项目需要：

- 路由（哪个 URL 对应哪个方法）
- 参数绑定（请求参数怎么变成方法参数）
- 返回值处理（返回对象怎么变成 JSON）
- 拦截器、异常处理、视图解析……

Spring MVC 把这些都封装好了。你写的是：

```
@GetMapping("/user/{id}")
public User getUser(@PathVariable Long id) { ... }
```

而不是去实现 `Servlet.service()`。Spring MVC 跑在 Servlet 容器（Tomcat）里，它自己内部也是通过一个 Servlet 来接入的—— DispatcherServlet。



2、DispatcherServlet

（1）为什么需要DispatcherServlet

Tomcat原生找Servlet：

Tomcat 依据 Servlet 规范，通过 `web.xml`（或注解）里的 `<url-pattern>` 把 URL 映射到某个 Servlet：

```
<servlet-mapping>
    <servlet-name>userServlet</servlet-name>
    <url-pattern>/user</url-pattern>
</servlet-mapping>
```

这意味着：一个 URL 模式对应一个 Servlet 类。

如果你想写一个用户模块，有增删改查四个操作，原生写法要么：

- 写 4 个 Servlet（`/user/add`、`/user/delete`…），类爆炸；
- 要么写 1 个 Servlet，在里面用 `if (path.equals("/add")) ... else if ...` 手动判断，逻辑臃肿、难以维护。

而且每个 Servlet 都要自己处理：参数解析、类型转换、校验、视图渲染、异常处理、拦截器……大量重复代码。



这个时候就需要统一的入口去处理

`DispatcherServlet` 本质是一个 Front Controller（前端控制器）。它把自己映射到 `/`（或 `/xxx/*`），拦截所有请求，然后由它内部再分发给真正的业务处理方法。Tomcat 仍然在做它擅长的事——根据 URL 找到 DispatcherServlet；而“请求怎么落到具体某个方法”这件事，交给了 SpringMVC 自己的一套机制。



Tomcat 解决的是“请求级别”的路由，SpringMVC 解决的是“方法级别”的路由和整套 Web 层的横切关注点。

| 问题                       | 原生 Servlet                    | DispatcherServlet                |
| :------------------------- | :------------------------------ | :------------------------------- |
| URL → 处理逻辑             | 一个 URL 一个 Servlet/if-else   | `@RequestMapping` 自动映射到方法 |
| 参数获取                   | `request.getParameter()` 手动取 | 方法参数自动绑定、类型转换       |
| 返回值                     | 手动 `response.getWriter()`     | 自动转 JSON/视图                 |
| 拦截器/AOP                 | 每个 Servlet 自己写             | 统一 HandlerInterceptor          |
| 异常处理                   | try-catch 到处写                | `@ExceptionHandler` 统一处理     |
| 视图解析                   | 手动 forward                    | ViewResolver                     |
| 文件上传、国际化、数据校验 | 各自实现                        | 统一组件                         |

- Tomcat 的查找：URL → Servlet 实例（粒度粗，一个 Servlet 一个入口）
- SpringMVC 的查找：URL → Controller 里的某个方法（粒度细，靠 `HandlerMapping`）

`DispatcherServlet` 本身就是一个普通的 Servlet，它依赖 Tomcat 才能被找到。二者不是替代关系，而是**分层协作**：

> Tomcat 是“高速公路的出口”，DispatcherServlet 是“出口后的城市路网导航”。





DispatcherServlet 是 Spring MVC 的核心，是一个 Servlet。它是 Spring MVC 的**前端控制器（Front Controller）**。所有请求先到它这里，由它统一调度：

```
浏览器请求 → Tomcat → DispatcherServlet（唯一的入口 Servlet）→ 
根据 URL 找到对应的 @Controller 方法 → 
执行方法 → 处理返回值 → 写回响应
```

你项目里那些 `@Controller`、`@RestController` 的方法，**没有一个是 Servlet**。它们只是被 `DispatcherServlet.doDispatch()` 通过反射调用的普通 Java 方法。DispatcherServlet 才是真正注册到 Tomcat 的那个 Servlet，真正被 Tomcat 当作 Servlet 调用的。通常在 `web.xml` 或 Spring Boot 自动配置里能看到它被映射到 `/`，意思是“所有请求都先交给它”。

```
浏览器
  │  HTTP 请求
  ▼
┌─────────────────────────────────────┐
│  Tomcat（Servlet 容器）              │
│  负责网络、线程、解析 HTTP            │
│                                     │
│  ┌───────────────────────────────┐  │
│  │ DispatcherServlet（一个 Servlet）│ │
│  │ Spring MVC 的前端控制器          │ │
│  │                               │  │
│  │  ┌─────────────────────────┐  │  │
│  │  │ @Controller 方法         │  │  │
│  │  │ （你的业务代码）          │  │  │
│  │  └─────────────────────────┘  │  │
│  │                               │  │
│  │  异步时：startAsync()          │  │
│  │  → AsyncContext               │  │
│  │  → SseEmitter 基于它实现       │  │
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘



Tomcat 线程
   │
   │ 调用 service()
   ▼
DispatcherServlet.service()          ← 继承自 HttpServlet
   │
   │ 按 HTTP 方法分发
   ▼
DispatcherServlet.doGet() / doPost() ← DispatcherServlet 重写，把它们统一收敛到 `doDispatch()`
   │

DispatcherServlet.doDispatch()       ← Spring MVC 核心调度，是 Spring MVC 真正干活的地方：找 handler、执行、处理返回值
   │

   ├─ 执行方法
   ├─ 处理返回值（视图 / JSON / SseEmitter…）
   └─ 写回响应
```





### 5、SocketChannel

（1）概述

`SocketChannel` 是 Java NIO 中代表**一个 TCP 连接**的通道。你可以把它理解成**一条双向管道**：一端连着 Tomcat，另一端连着客户端。所有 HTTP 请求的读取和响应的写回，最终都是通过它完成的。

是什么：

在 Java NIO 中：

- `ServerSocketChannel`：监听端口，负责**接收新连接**（对应 Acceptor 线程）

- `SocketChannel`：代表**一个已建立的 TCP 连接**，负责**读写数据**

```
ServerSocketChannel (监听 8080)
        │
        │ accept()
        ▼
SocketChannel (连接 A)  ←→ 客户端 A
SocketChannel (连接 B)  ←→ 客户端 B
SocketChannel (连接 C)  ←→ 客户端 C
```

每来一个客户端连接，Acceptor 就创建一个 `SocketChannel`，之后这个连接的所有读写都走它。

一个 HTTP 请求的完整生命周期，读写都绑定在同一个 `SocketChannel` 上：

| 阶段      | 操作                                  | 方向            |
| :-------- | :------------------------------------ | :-------------- |
| 请求到达  | 从 `SocketChannel` **读**字节         | 客户端 → Tomcat |
| 解析 HTTP | 读到的字节解析成 `HttpServletRequest` | —               |
| 业务处理  | 生成响应数据                          | —               |
| 响应写回  | 往 `SocketChannel` **写**字节         | Tomcat → 客户端 |

- **读请求**：Poller 监听 `OP_READ`，发现 `SocketChannel` 有数据可读。
- **写响应**：Executor 或业务线程往 `SocketChannel` 写数据。



（2）SocketChannel 和缓冲区的关系：

`SocketChannel` 本身不存数据，它只是通道。数据实际存在**内核的 TCP 缓冲区**里：

```
应用程序
   │
   │ write() / read()
   ▼
SocketChannel（通道，不存数据）
   │
   ▼
内核 TCP 发送缓冲区 / 接收缓冲区（真正存数据的地方）
   │
   ▼
网卡 → 网络
```

- **写**：应用调 `write()` → 数据进发送缓冲区 → 内核逐步发出去。
- **读**：数据到达接收缓冲区 → Poller 监听到 `OP_READ` → 应用调 `read()` 取走。



（3）结合Tomcat完整视角

```
客户端                     Tomcat
  │                          │
  │──TCP 连接──→  ServerSocketChannel.accept()
  │                    │
  │                    ▼
  │              SocketChannel（代表这条连接）
  │                    │
  │──HTTP 请求──→  接收缓冲区 → Poller 监听 OP_READ
  │                    │ Executor 线程 read() 解析
  │                    │ 执行业务
  │                    │
  │←──HTTP 响应──  发送缓冲区 ← Executor/业务线程 write()
  │                    │ （写不完则注册 OP_WRITE，Poller 监听可写）
```

和SseEmitter的联系：

- Controller 返回 `SseEmitter` 时，Spring 把这个 Emitter 和当前请求的 **`SocketChannel`**（通过 `ServletResponse` 输出流）绑定。
- 后续每次 `emitter.send(data)`，本质就是往这个 `SocketChannel` 的发送缓冲区写数据。
- 如果写不完，Tomcat 就在这个 `SocketChannel` 上注册 `OP_WRITE`，由 Poller 监听可写后唤醒线程（当初调用 `write()` 写不完的那个线程本身）继续写。

所以 SseEmitter 不直接操作 SocketChannel，它操作的是 Spring/Tomcat 封装好的输出流，底层最终落到 `SocketChannel`。

（5）总结

`SocketChannel` 是 Java NIO 中**一条 TCP 连接**的抽象，HTTP 请求的读取和响应的写回，最终都通过它完成。它本身不存数据，数据存在内核的 TCP 缓冲区里，Poller 监听的就是这个通道上的读写事件。





### 6、TCP缓冲区

（1）概述

TCP 缓冲区是操作系统内核为每个 TCP 连接维护的**内存区域**，分为**发送缓冲区**和**接收缓冲区**。它是 TCP 可靠传输和流量控制的核心机制。



（2）为什么需要缓冲区

TCP 是面向流的协议，应用程序和网络之间的速度不匹配：

- **应用层**：可能一次写 1MB 数据，但网卡一次只能发 1500 字节。
- **网络层**：数据到达速度可能忽快忽慢，应用层处理速度也不稳定。

缓冲区就是中间的"蓄水池"，**解耦生产者和消费者的速度差异**。



（3）发送缓冲区（Send Buffer）

**位置**：内核中，属于发送方。

**作用**：应用程序调用 `write()` 时，数据先拷贝到发送缓冲区，内核再根据网络情况逐步发送。

```
应用程序 write() → 发送缓冲区 → TCP 分段 → 网卡 → 网络
```

**关键点**：

- `write()` 返回成功，**只代表数据进入了发送缓冲区**，不代表对方收到了。
- 如果发送缓冲区满了，`write()` 会阻塞（阻塞模式）或返回部分写入（非阻塞模式）。
- 数据会一直保留在缓冲区，直到收到对方的 **ACK 确认**后才释放。



（4）接收缓冲区（Receive Buffer）

**位置**：内核中，属于接收方。

**作用**：网络数据到达后，先放入接收缓冲区，应用程序再调用 `read()` 从中读取。

```
网卡 → 接收缓冲区 → 应用程序 read()
```

**关键点**：

- 数据到达时，如果应用程序还没调用 `read()`，数据就暂存在接收缓冲区。
- 如果接收缓冲区满了，TCP 会通过**滑动窗口**告诉发送方"我这边满了，先别发"，这就是**流量控制**。
- Poller 监听 `OP_READ`，本质就是监听"接收缓冲区是否有数据可读"。



（5）结合Tomcat

```
客户端                                    服务器（Tomcat）
  │                                          │
  │──HTTP 请求──→ [服务器接收缓冲区] ──→ Poller 监听 OP_READ
  │                                          │ Executor read() 读走数据
  │                                          │ 解析 HTTP，执行业务
  │                                          │
  │←──HTTP 响应── [服务器发送缓冲区] ←── Executor write()
  │                                          │
  │  （如果发送缓冲区满，注册 OP_WRITE，    │
  │    Poller 监听可写后再继续写）           │
```

| 缓冲区     | 所属   | 触发的事件 | Tomcat 中的角色                           |
| :--------- | :----- | :--------- | :---------------------------------------- |
| 接收缓冲区 | 服务器 | `OP_READ`  | Poller 发现有数据可读，派发给 Executor    |
| 发送缓冲区 | 服务器 | `OP_WRITE` | 写不完时 Poller 监听可写，派发给 Executor |





## 二、SseEmitter



````
好问题。`SseEmitter` 不是在某“一步”介入，而是**横跨③到⑦**，它本身就是对这套异步机制的封装。我们把它拆进流程里看。

---

## 一、SseEmitter 在哪一步被创建

关键点：**你在 `service()` 执行期间（即第③步附近）就创建并返回了 `SseEmitter`。**

```java
@GetMapping("/stream")
public SseEmitter stream() {        // ← 这个方法在 Tomcat 线程里执行
    SseEmitter emitter = new SseEmitter();   // ← 创建
    executor.execute(() -> { ... });         // ← 交给业务线程池
    return emitter;                          // ← 返回
}
```

这个 `@GetMapping` 方法是被 `DispatcherServlet.doDispatch()` 调用的，而 `doDispatch()` 运行在 **Tomcat 线程**上。所以：

- **创建 `SseEmitter`**：在 Tomcat 线程里
- **返回 `SseEmitter`**：在 Tomcat 线程里

---

## 二、SseEmitter 触发了 startAsync

这是最关键的一环。当 `DispatcherServlet` 拿到你返回的 `SseEmitter` 时，它发现这是个异步返回值，于是**替你把 `request.startAsync()` 调了**：

```
DispatcherServlet.doDispatch()
   │
   │ 发现返回值是 SseEmitter（异步类型）
   ▼
调用 request.startAsync()  →  拿到 AsyncContext
   │
   ▼
把 AsyncContext 交给 SseEmitter 管理
   │
   ▼
service() 返回，Tomcat 线程归还 ✅
```

所以第③步的 `startAsync()` **不是你手动调的，是 Spring MVC 看到 `SseEmitter` 后自动调的**。你只是“声明了我要异步”，Spring 帮你完成底层操作。

---

## 三、SseEmitter 在业务阶段的干预（第⑤⑥步）

`SseEmitter` 内部持有了 `AsyncContext`。当你在业务线程里调用：

```java
emitter.send(data);
```

它内部实际做的是：

```
emitter.send(data)
   │
   ▼
把 data 格式化成 SSE 格式（"data: xxx\n\n"）
   │
   ▼
通过 AsyncContext.getResponse().getWriter().write(...) 写出
   │
   ▼
flush，立刻发给客户端
```

所以**第⑥步的“写响应”，就是通过 `emitter.send()` 完成的**。你不是直接操作 `AsyncContext`，而是通过 `SseEmitter` 这个封装层。

同理：

- `emitter.complete()` → 内部调 `asyncContext.complete()`
- `emitter.completeWithError(e)` → 内部调 `asyncContext.complete()` 并带错误
- `emitter.onTimeout(...)` → 注册到 `AsyncContext` 的超时回调

---

## 四、把 SseEmitter 放进流程图

```
① 浏览器发请求

        ▼

        │
        ▼
④ service() 返回 ──────────────► Tomcat 线程归还池子 ✅
        │
        │ 你在方法里已把任务提交给业务线程池
        ▼
⑤ 业务线程池（你自己建的）
   执行慢操作 / 循环产生数据
        │
        ▼
⑥ emitter.send(data)                        ← 【SseEmitter 在这里干预】

   （循环多次）
        │
        ▼
⑦ emitter.complete()                        ← 【SseEmitter 在这里干预】

```

## 五、和“手动 AsyncContext”的对比

如果不使用 `SseEmitter`，你得自己写：

```java
@GetMapping("/stream")
public void stream(HttpServletRequest request, HttpServletResponse response) {
    AsyncContext asyncContext = request.startAsync();   // 手动 startAsync
    executor.execute(() -> {
        try {
            PrintWriter writer = asyncContext.getResponse().getWriter();
            while (true) {
                writer.write("data: " + getData() + "\n\n");
                writer.flush();
                Thread.sleep(1000);
            }
        } catch (Exception e) {
            // 错误处理
        } finally {
            asyncContext.complete();                    // 手动 complete
        }
    });
}
```

对比一下：

| 操作 | 手动 AsyncContext | SseEmitter |
|------|-------------------|------------|
| 启动异步 | 手动 `request.startAsync()` | Spring 自动调 |
| 管理 AsyncContext | 自己持有 | SseEmitter 内部持有 |
| 写数据 | 手动拼 SSE 格式 + write + flush | `emitter.send(data)` |
| 完成 | 手动 `complete()` | `emitter.complete()` |
| 错误处理 | 自己 try-catch | `completeWithError()` |
| 超时 | 自己配 | `new SseEmitter(timeout)` |

**`SseEmitter` = 手动 AsyncContext 的封装 + SSE 格式处理 + 生命周期回调。**

## 六、一句话回答

`SseEmitter` 的干预贯穿全程：

- **创建和返回**：在第③步，Tomcat 线程里，由你的 Controller 方法完成
- **触发 startAsync**：在第③步，由 Spring MVC 发现返回值后自动完成
- **写数据**：在第⑥步，由业务线程调用 `emitter.send()` 完成
- **结束**：在第⑦步，由 `emitter.complete()` 触发 `asyncContext.complete()`

它不是“某一步的干预者”，而是**整个异步 + SSE 流程的封装层**。你写 `SseEmitter`，就等于在写“手动 AsyncContext + SSE 格式 + 生命周期管理”的完整代码，只是 Spring 帮你把底层都包好了。
````
